# 真机验证清单（首条价值切片）

**谁来做**：你（不需要读代码）。**何时**：Task 6 之后随时；识物/造句反馈接上后（Task 7/8）需再走一遍第 5–16 步。

**为什么必须人工做**：自动化测试能覆盖纯逻辑与装配，但**相机权限、真机渲染、`getUserMedia` 行为、真实拍照的明暗判定**这四类只能在手机上确认。subagent 已明令不得声称完成这些步骤。

> **Task 7 之后本清单的更新（2026-09-14，只列变化，逐字覆盖上面表格里的旧预期）**
>
> | 项 | 变化 |
> |---|---|
> | 第 8 步 | **"说明识物尚未接入"这条预期作废**。识物已接入：这一屏应当显示**一个真实的英文词**（对着马克杯应出现 `mug` 或 `cup`），并附一行"场景：… 第 N 次尝试取到"。**若这一屏出现英文单词但你没拍到任何东西，那是缺陷，不是功能** |
> | 第 9/10 步 | 不变（太暗/太糊仍当场退回）。新增：被退回时**服务端不应有任何识物调用**——见下面控制器追加的 D 项 |
> | 第 13 步 | 不变（跳屏后相机灯要灭） |
> | 新增 | **识物成功路径**（下面 18）、**识物失败降级到手选**（19）、**手选不冒充识别结果**（20）、**"再拍一张"**（21） |
>
> 第 5–7、11、12、14–17 步逐字不变。

## Task 7 专项：识物链路（手机上是必看项）

| # | 检查项 | 预期现象 |
|---|---|---|
| 18 | **识物真的能取到词** | 对准一个马克杯（或杯子）→ 按快门 → 1–3 秒后出现一个**具体的英文名词**（`mug` / `cup`）；标题下方那行应写明"场景：…"与"第 N 次尝试取到"。**不应**出现 `container`、`object`、`thing` 这类上位词——那些词被 `pickWord` 挡掉了，出现即缺陷 |
| 19 | **取不到词时降级为手选，且不假造** | 对着一个模型多半认不出的东西拍（例如纯色墙面、手掌、模糊远景）→ 两轮尝试后应显示"**没能自动认出这个词**"，下面是一排可点的英文词（`mug` `cup` `book` …）与一个「再拍一张」。**这一屏不许出现任何"识别出来的词"** |
| 20 | **手选的词明说是手选** | 在第 19 步的列表里点一个词 → 标题变成那个词，下面那行必须写"**这是你自己挑的词，不是识别出来的**"。若这句没出现，就是把手选冒充成了识别结果 |
| 21 | **「再拍一张」立刻重来** | 在 19/20 那屏点「再拍一张」→ 应**立刻再拍一帧并重走一次识物**（不需要退回首页再点拍照）。连点两三次不卡死、不白屏 |
| 22 | **识别失败不等于帧被拒** | 走完第 19 步后回到首页看你拍了几次：识物失败**不应**被计成"被退回的帧"（那是"太暗/太糊"专用的计数）。完成页「被退回的帧」应只统计太暗/太糊的次数 |

## 控制器追加的三项（不在原清单内，但必须确认）

| # | 检查项 | 为什么重要 |
|---|---|---|
| **A** | **一条畸形请求不会打死服务**：在电脑上执行<br>`curl -i "http://localhost:8787//"`<br>预期：返回 `400 Bad Request`，且服务**仍在运行**（随后正常访问页面仍可用） | 修复前 `GET //` 会让服务进程 `exit 1`。修复已由控制器复现并验证，**但需要你在隧道环境下确认一次** |
| **B** | **句子是否真的入库**：走完第 16 步后，打开浏览器开发者工具 → Application → Local Storage，查看键 `elp.events`，搜索你写的那句话 | Task 6 刻意把 `compose_submitted` 延后到 Task 9——**接线前你的句子不会持久化**。这一项确认它到底存没存；没存属已知状态，存了更好 |
| **C** | **隧道期间的额度消耗**：服务开着隧道时，确认是否有他人/扫描器调用 `/api/recognize` 或 `/api/feedback` | Task 7/8 接上真实模型后，这两个端点会**消耗你的 DeepSeek 额度**。密钥不会泄漏（只在服务端），但额度会。**若长时间挂公网，需加访问口令或限流，或只在测试时开、用完即关**。补充：识物端点在**收到没有图片的请求时会直接回 400、不打上游**（因此扫描器打不穿额度），但**带图片的请求会真的调用模型**，仍按一次识物计费 |
| **D** | **被拒的帧不花额度**：对着纯黑/纯色画面拍，看到"太暗/太糊"提示后，回电脑看服务端终端日志 | 预期：**没有任何识物相关日志行**（帧在端侧就被拦下了）。若出现一行 `recognize 失败`/`识物请求`，说明前置拦截失效，额度会白白消耗 |
| **E** | **手选不产生识别成功记录**：走完第 19–20 步（手选一个词）后，导出或翻查本地事件记录 | 预期：这一轮落的是 `recognize_failed`（带 `reason`，例如 `no_candidates` / `not_in_acceptable_set` / `request_failed`），**不是** `recognize_ok`。若手选也记了 `recognize_ok`，识物成功率会被手选污染 |

| 9 | **太暗会被退回** | 用手完全挡住镜头再拍 → 退回初始页并提示"刚才那张太暗…"，**不是**跳到"取到的词" |
| 10 | **太糊会被退回** | 对着白墙或纯色平面（无纹理）拍 → 退回并提示"有点糊…" |
| 11 | **重拍能连续进行** | 被退回后立刻再拍，重复 3 次不卡死、不白屏 |
| 12 | **按太早的表现** | 刚进拍摄画面、画面还没出来时连点「快门」→ 提示"画面还没准备好，请稍等一秒"，**不应**跳到"取到的词" |
| 13 | **摄像头灯会灭** | 从拍摄屏跳到"取到的词"后，状态栏/刘海处**相机指示灯应熄灭**（若一直亮，记录机型） |
| 14 | **双击不会卡住** | 初始页快速双击「拍照」→ 正常进入拍摄画面，不出现两路画面或两次权限弹窗 |
| 15 | **屏幕适配** | 内容不被刘海/挖孔挡住；按钮与输入框不超屏；横竖屏切换不破版 |
| 16 | **整个骨架能走完** | 拍照 → 快门 → 「我会读了」→「跳过跟读」或「我读完了」→ 写一句英文 →「提交造句」→「再写一次」（**输入框应带出上一版原文**）→「提交造句」→「下一个词」→ 完成页显示「**改写 1 次**」等指标（提交 2 次 = 回改 1 版） |
| 17 | **刷新页面后** | 回到初始页（当前不跨页面保存进度）；**相机权限不应再次询问** |

> ⚠️ 第 16 步的预期值是「改写 **1** 次」。早期文档曾写「改写 2 次」，那是把提交次数误当改写次数的旧缺陷（已修）。**若你照旧文走查，会误报一个已经修好的问题。**

## 回报什么

1. **手机型号 + 浏览器与版本**（第 6、13 项需要）
2. 每一步的实际现象：成功 / 失败 / **提示原文**
3. 任何"没有反应"或白屏的时刻
4. **即使全部通过也要回报"全部通过"** —— 沉默无法区分"通过"与"没测"

## 已知的、不算问题的现象

- 第 9/10 步的阈值（亮度 40 / 清晰度 80）是**首轮设定值，未经真实数据校准**。若你觉得明显偏松或偏严（例如正常室内光也被判太暗），**如实记录当时的场景与现象**——这正是首周校准要用的数据。
