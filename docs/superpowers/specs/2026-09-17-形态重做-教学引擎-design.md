## 0. 为什么会有这份文档（前情与一次认知修正）

本项目 09-14 的原始设计 spec 与实施计划里，**没有任何界面设计**：无屏幕清单、无信息架构、无导航形态、无版式、无视觉方向、无参考图。计划对界面的全部投入 = Task 6 里 6 行内联 `<style>`。界面是在实现里长出来的，直到 09-17 才第一次被当成一件事处理——所以"简陋"的根因不是**旧设计过时**，而是**从来没有设计过**。

更重要的是一次认知修正：设计初期把 `SCENE_FIRST` 理解成了**相机中心**的形态（把日常物品识别成词）。用户否掉了这条：

> 「软件应当引导用户自己去看，自己去想，而不是一味借助相机识别。大多数时候，用户知道他看见的东西用中文怎么说，需要拍照识别的东西很少，而且那部分现有的产品预期做不到。重要的是英语学习本身，不是各种花里胡哨的假装 nb 的功能。」

这条批评成立，理由有三：
1. **识物解决的不是用户的问题。** 用户知道自己看见的是"马克杯"，他的困难是**说不出英文**。
2. **给答案会杀死学习。** 识别 → 显示 → 点头，学习者什么都没做。学习发生在**检索**（努力调出）而非**接收**。
3. **相机中心与"生活化"是两件事。** 词应当来自**学习者自己的注意力**，不是来自某次物体检测。

由此确立本稿的第一原则。

---

## 1. 第一原则

> **相机退居次要。教学法是产品。系统引导用户自己去看、自己想；给答案只在用户已经努力之后。**

推论：
- 产品的差异化不在"识别能力"，而在**教学引擎**（提问方法 + 知识资产 + 引导纪律）。
- 任何"看起来很 nb 但用户不需要"的能力都不做（用户原话：不搞"花里胡哨的假装 nb 的功能"）。
- 识物不删除，但降级为**学习者主动求助时的一条查询路径**，而不是产品的主动脉。

## 2. 中枢：一次对话，按需换挡

形态不是"每日问卷"，也不是"聊天机器人"。是**一次围绕学习者内容的对话**，系统在对话中不断判断"此刻该做哪种教学动作"。

### 2.1 内容从哪来（解决了"替学习者规定世界"的问题）

两种来源，**用户的焦点优先**：
1. **用户带来内容**：他今天干了什么、想说什么、遇到的一个句子。系统**按他的内容**挑出教学点。
2. **系统给情境**：当没有用户内容、或需要刻意复现某个词/结构时，系统造一个情境。

设计原则：**系统不能替学习者决定他的世界**。如果每次只推系统选的词，那还是在替他规定该注意什么。

优先级规则（写死，防歧义）：
1. **用户有内容 → 只用用户的内容**，教学点从他的内容里挑。
2. **用户没有内容 → 系统才给情境**，且要**邀请他补充**自己的东西（"有没有一件跟你今天有关的事？"）。
3. 系统自选情境**不得连续两次**成为会话起点，否则形态会退回"系统规定世界"。

### 2.2 教学循环（四拍）

```
诊断 → 搭台 → 逼产出 → 给够用的帮助
```

1. **诊断**：对当前焦点，判断学习者现在能做什么（能产出？认得？完全不会？）。诊断不能靠直接问"你会吗"——要靠**让他做**。
2. **搭台**：给一个**需要用到**该词/该结构的情境或任务。台子不能太难（打击）也不能太易（无学习）。
3. **逼产出**：学习者说或写。**这一步不许跳过**——没有产出就没有诊断，也没有学习。
4. **给够用的帮助**：不是替他做完，而是给到他能往下走的**最小**帮助（一个词、一个句型、一个提示）。

### 2.3 引导纪律（写死的硬约束）

- **不替用户决定下一步**：系统给**选项**，用户选。系统可以说"我建议先…"，不能说"现在是第三关"。
- **默认姿态是配合，不是纠正**：学习者的自由产出首先被当作**表达**，不是**待批改的作业**。纠正只在特定时刻发生（见 §2.5）。这是与 `NON_GOALS` 里"应试技巧"划清界限的地方。
- **不审讯**：任何提问方式**连续使用即失效**。系统必须记录"最近用过哪些方式"，避免重复施压。
- **不制造焦虑**：不威胁、不计分、不排榜、不比较他人。

## 3. 提问方法库（本稿的核心资产）

这是"提问需有方法"的正面回答。每种方法都要回答：**什么时候用、怎么用、失败长什么样**。

### 3.1 为什么需要"库"而不是"一个流程"

要学习者用上"犹豫 / hesitate"，问"你今天怎么样"是错的。正确做法是**造一个他必须犹豫的情境**。所以：
- **方法不是外壳，方法就是教学引擎**。
- 同一个词，用不同方法教，效果不同 → 需要**方法 × 目标**的匹配表。
- 没有一种方法永远好 → 需要**换挡**。

### 3.2 方法目录（初版九种）

| 方法 | 机制 | 最适合 | 失败模式（必须防） |
|---|---|---|---|
| **角色扮演** | 给一个情境与角色，学习者必须用目标语完成交流 | 产出完整句子、时态/礼貌层级、真实语用 | 情境假、学习者出戏、系统抢话 |
| **任务驱动** | 给一个可完成的小任务（订房、投诉、问路），语言是手段 | 功能性表达、搭配 | 任务太难 → 卡死 |
| **描述与命名** | 让学习者描述眼前/回忆中的人事物 | 词汇广度、名词短语、形容词 | 变成"识物"（退回相机中心） |
| **翻译对照** | 给中文，学习者说英文；再对照地道说法 | 中式英语暴露、搭配 | 变成逐句批改 → 应试 |
| **半句接龙** | 给半句，学习者补完 | 语法结构、连接词 | 变成填空 → 机械 |
| **情境猜词** | 用英文描述，让学习者猜是哪个词 | 建立"英文释义"通路，脱离中文中介 | 描述过难 → 挫败 |
| **回忆叙述** | 引导回忆真实经历，讲出来 | 过去时、叙述连贯（用户举的例） | **每天问"今天怎么样"会烦** |
| **纠错反思** | 拿学习者**自己写过的**内容，一起看哪里可以更好 | 元认知、自我修正 | 变成挑错 → 打击 |
| **扩展与升格** | 同一内容换说法/升格（句子 → 段落 → 风格化） | 表达的层次与丰富度 | 拔太高 → 假大空 |

### 3.3 换挡判据（何时该换方法）

换挡不是随机的，由**信号**触发：

| 观察到的信号 | 含义 | 换挡方向 |
|---|---|---|
| 学习者答得太快且全对 | 台子太易 | 升难度 / 换更开放的方法 |
| 学习者沉默、只说"不知道" | 台子太难 或 方法不对路 | 降难度 / 换更结构化的方法（半句接龙、猜词） |
| 同一方法连续 2 次 | 新鲜度耗尽 | **强制换方法** |
| 学习者主动说想学 X | 动机窗口 | 立刻切到他的焦点 |
| 学习者开始用自己的话讲 | 进入表达状态 | **系统闭嘴**，只在被问时帮 |
| 同一错误反复出现 | 真实薄弱点 | 进入刻意复现（见 §5） |

### 3.4 这是"框架约束模型"的具体形态

用户要求：*「模型采用我们应用的特殊框架约束，并拥有英语专精知识库支撑」*。落到实现上即：
- 模型**不自由发挥**教学内容：教什么由**知识资产 + 学习者状态**决定。
- 模型的职责 = 在给定焦点与方法下**生成这一次的话术**，并按框架要求**选择引导动作**。
- 因此提示词不是"你是一个英语老师"，而是"你在这套框架的第 N 拍，用第 M 种方法，针对焦点 F，学习者当前状态 S，产出下一步"。

具体形态（示例，待实现时定稿）：

```
【框架】这一次你处在"逼产出"这一拍。方法=角色扮演。
【焦点】hesitate（词）——来自用户今天的内容。
【学习者状态】认得，未产出过。
【情境】退租时跟房东说要再考虑两天。
【要求】你只演房东，说 1-2 句；必须给对方留出使用 hesitate 的机会；
        不要说出 hesitate 这个词；不要评价他的英语；他产出后再进入下一拍。
【禁止】讲解 hesitate 的用法、给出一整段范文、连续追问超过 2 轮。
```

要点：**约束是"行为约束"而不是"角色约束"**——角色设定（"你是英语老师"）保证不了教学质量，行为约束（不许说这个词、不许连续追问、必须留出使用机会）才能。

## 4. 知识资产（新形态的必备品，现有仓库一条都没有）

| 资产 | 内容 | 为什么必须有 |
|---|---|---|
| **重点词库** | 词 + 词族 + 搭配 + 例句 + **易混词对比** | 判断"哪些值得教"；避免教了冷僻词 |
| **语法点库** | 点 + **中国人常错模式** + 最小对比对 | 精准命中"你这一句里的那个点"，而不是讲一章语法 |
| **表达优化库** | 中式英语典型模式 → 地道替换路径 | 这是"优化表达"能成立的前提 |
| **阶梯框架** | 每层的引导话术与推进判据 | §3 的方法库需要它来落地 |
| **情境库** | 生活化情境（居家/通勤/职场/餐饮…），每个情境带可用词与结构 | 角色扮演/任务驱动需要现成台子 |
| **学习者长期语料** | 他写过的每一天、犯过的错、用过的词 | **产品最值钱的资产**；"循序渐进"的前提 |

> ⚠️ 这六项里，前三项是**内容工程**，不是写代码。需要在计划里单独排期与定验收口径——否则会变成"先写引擎，内容永远没到位"。

## 5. 复现：从"排期驱动"改成"对话内自然复现"

现在 `scheduler.mjs` 是 1/3/7 天固定间隔、到点催。在新形态里：
- **复现的载体是对话**，不是提醒。系统在新情境里**自然要求**用上旧词（"你上次说你去看了电影——这次用英文讲讲那次电影"）。
- 固定间隔**可以作为后台线索**（何时该把某个旧词编进新情境），但**不作为对用户的指令**（不发"该复习了"）。
- 代价：现在 `dueWords` / `stage` / 到期徽标这一整条**用户可见的排期面**要退场或彻底重做。

## 8. 作品化：不靠进度条解决"拥有感"

`IN_SCOPE` 已承诺「个人进度与已掌握词可视化」。新形态下最强的可视化不是图表，而是：

> **回看你自己的作品。** 你第一天写的东西、系统陪你改过几轮、现在你能怎么写同一件事——这本**你自己的英文日记**就是进度。

好处：同时解决"拥有感"与"留存来源"（留存来自**这是我写的东西**，而非打卡），并且与 `NON_GOALS` 不冲突。

## 9. 待回答的问题（新契约要回答什么）

旧 `GOAL` 要回答"成人愿不愿意为一次取词举起手机拍一下"。新形态下这个问题**失效**，需要换成：

1. 成人愿不愿意**每天花几分钟把自己的生活用英语说一遍**？
2. **引导式对话**能不能让他持续产出（而不是三天后放弃）？
3. 经过若干次对话，他的**表达**（用词/搭配/连贯）是否可观测地变好？

> 这三条才是新契约的验收命题，且第 3 条可以机读（对同一内容的前后产出做对比），不依赖人工评分。

## 11. 风险（必须先摆平，否则形态定了也落不了地）

1. **自带 Key 的成本结构变了。** 现在是两次调用/词；对话形态是**一次会话多轮调用**。对免费试用的心理门槛是实质抬高的——陌生人要拿自己的钱跑一段不知道多长的对话。需要明确：一次会话的调用上限与用户可见的成本预期。
2. **`NON_GOALS` 撞车（每日任务）**。"每日任务"极容易滑向打卡；必须写死"无连续天数、无断签惩罚"。它只能是"每日一次引导"，不是"任务"。
3. **长期语料 = 全部价值，但现在没有账号。** spec 明确不做账号体系（设备本地 ID）。在识物工具里这没问题；在"陪你学三个月"的产品里，**清一次浏览器数据就清空三个月积累**。这条从"可接受取舍"升级为**产品级风险**，需要正面处置（导出/导入至少要能在册）。
4. **内容工程会被无限推迟。** §4 前三项是内容，不是代码。若不在计划里单列，引擎会先写完而词库/语法库/优化库永远半成品。
5. **"闭嘴"很难实现。** §2.3 要求系统在学习者进入表达状态时停止纠正。这对提示词与状态机都是硬要求，且**很难测**——需要一个可观测判据。
