## 1. 目标与成功标准

**要交付的东西**：一个能被真人拿去用的学习闭环——拍照识物取词 → 跟读 → 自己造句 → 拿到反馈 → 该词在**新场景**中复现。用手机浏览器打开即用，无需安装。

**要回答的问题**：成人愿不愿意为一次取词举起手机拍一下，并愿意付出造句这份主动产出成本。这是验证一（`VAL-OPI-…36`）的真机版。

**成功标准（直接复用 dmcp 在册判据，不另造一套）**

| 判据 | 登记对象 | 门槛 |
|---|---|---|
| 识物 top-3 准确率 | `VAL-OPI-…38` | `>= 0.85`，3 轮取均值 |
| 重拍率 | `VAL-OPI-…50` | `<= 0.2`，3 轮取最差值（MAX） |
| 成人接受度 | `VAL-OPI-…36` | 5 项人类评分，2 轮取中位（>8/12 为暂立） |
| 造句反馈质量 | `VAL-OPI-…40` | 5 项人类评分，3 轮取中位 |

**不包含**：长期留存（`VAL-…42` 属 RELEASE 闸门）、音准评分、账号体系、离线可用。

## 3. 闭环与状态机（第 1 节）

### 3.1 七态

| 状态 | 屏幕上唯一的主动作 | 强制前置 | 退出后果 |
|---|---|---|---|
| `ready` | 拍照 / 选场景 | — | 记录为"进入未取词" |
| `capturing` | 按快门 | — | — |
| `word` | 看词、听发音 → 点"我会读了" | 必须有词 | — |
| `reading` | 跟读（按住说话） | 已看过词 | 可跳过，标记 `skipped_reading` |
| `composing` | 写/说一个句子 → 提交 | 已过 `reading` | **不可跳过** |
| `feedback` | 看反馈 → "再写一次" 或 "下一词" | 已提交句子 | — |
| `done` | 结束 | — | — |

**一个允许的小回环**：`feedback` →（点"再写一次"）→ `composing` → `feedback`。该回环**不设次数上限**，但每次进入 `composing` 都累加 `rewrite_count`（首次进入为 1）。`rewrite_count > 1` 是"这个用户真的在改"的正面信号；`rewrite_count = 1` 且停留时长短，是敷衍信号（§3.2）。

### 3.2 「造句不可跳过」是有意的

这是首版要测的那个成本本身。若允许随时退出，拿到的将是退出点分布，而不是"愿不愿意"的答案。

**代价与对策**：强制感会诱发敷衍——有人写一句极短的话交差。因此 `composing` 态必须记录**停留时长**与**改写次数**；事后按"时长过短 + 未改写"筛出敷衍样本，单独统计，不混入通过率。

### 3.3 数据流（一次闭环 ≈ 4 次网络往返）

```
拍照帧 ──→ [识物] ──→ 目标词 + 场景标签
                        │
用户朗读 ──→ [转写] ──→ 是否说出目标词（不做音素级评分，见 §5.3）
                        │
用户造句 ──→ [反馈] ──→ 判定 + 用词错/搭配不当 + 地道改写
                        │
                        └──→ 全量落盘（原句、反馈、耗时、改写次数）
```

### 3.4 「强制换场景」的确切含义（此处消歧）

词到期时，复现**不是**再把这张词卡显示一遍，而是：

1. `ready` 态改为显示一个**新的场景主题**（例：该词上次在"厨房"学得，这次推"通勤"）
2. 用户需在**新场景中重新拍照取词**
3. 系统在新场景的候选词中检索该目标词：
   - 命中 → 记为**跨场景复现成功**，`recurrence_mode = scene_reacquired`
   - 未命中（该场景确实取不到这个词）→ 界面提供"我要复现的词是 X"，用户手选，记为 `recurrence_mode = manual_reacquire`，并**单独统计**

**为何要分成两种模式**：手选是降级路径，若大量复现靠手选，说明"跨场景"这个主张在真实使用中并没有被兑现——这是必须看见的信号，不能混进一个总数里。

## 4. 核心单元与边界（第 2 节）

每个单元只做一件事，接口先定死，换实现不牵动其他单元。

| 单元 | 输入 → 输出 | 依赖 | 明确不负责 |
|---|---|---|---|
| `CameraSource` | 无 → 帧 Blob | `getUserMedia`、HTTPS | 不做任何识别判断 |
| `frameQC`（端侧） | 帧 → 通过 / 太暗 / 糊了 | Canvas 采样 | 不判断"是什么物体" |
| `RecognizeService` | 帧 → top-3 候选（词 + 场景标签） | 视觉模型 API | **不选词** |
| `PickWord` | 候选 → 1 个可用场景词 | 词表可接受集 | 不调模型 |
| `SpeakCheck` | 朗读 → 是否说出目标词 | Web Speech API 转写 | **不做音素级音准评分** |
| `FeedbackEngine` | 词 + 句 + 场景 → 结构化判定 | 文本模型 + schema 校验 | 不评发音 |
| `EventLog` | 任意事件 → 落盘 | 存储层 | 不解释数据 |
| `DueScheduler` | 词状态 + 时间 → 今日任务 | 本地存储 | 不联网、不做自适应 |

### 4.1 三候选 + 人工重拍，不做自动连拍

`retry_rate` 已是正式闸门。**若系统自动连拍兜底，就永远测不出真实的"要不要重拍"**——而那正是最需要知道的事。因此第一帧不合格时，由用户决定是否再拍。

### 4.2 `FeedbackEngine` 必须有 `uncertain` 档

LLM 对单句判定时"拿不准"是真实状态。若 schema 只允许二元判定，模型会在不确定时被迫编一个**有信心的错误答案**。受污染的数据比没数据更糟。

**响应契约（严格校验，不合规即视为失败，不猜测修补）**

```json
{
  "verdict": "correct | flawed | uncertain",
  "error_type": "word_choice | collocation | grammar | none",
  "rewrite": "更地道的改写，或 null",
  "note": "一句话说明，面向学习者，不堆术语"
}
```

- `verdict = uncertain` 时：界面如实显示"这句我拿不准"，仍给改写建议
- `uncertain` **单独统计**，不计入通过率
- 任何字段缺失或取值越界 → 走 `feedback_pending`（§5），不猜测填充

### 4.3 发音只判"有没有说出目标词"

Web Speech API 返回的是**转写文本**，不是音素。硬做音准评分只能靠猜，等于伪造能力。首版只回答"你有没有把这个词念出来"。

**这是对契约的显式妥协**：`TECHNICAL_CONSTRAINTS` 中"发音评测需在移动端本地或低延迟链路完成"一条，在首版**未满足**。音准评分留给原生版，且必须在那时用真实音素能力兑现，不得用转写近似冒充。

### 4.4 首版明确不做

账号体系（用设备本地 ID）、离线可用、自适应间隔算法（固定 1/3/7 天，见 §4.5）、管理后台（导出 CSV/JSON 即可）、音准评分。

### 4.5 复现生命周期（此处消歧）

- 一个词**学完即入队**，间隔固定 **1 天 → 3 天 → 7 天**
- 每次到期需在新场景中重新取词（§3.4）
- 7 天档完成后再到期 → 状态转为 `maintained`，**不再主动推送**，但数据保留
- 用户在造句后自评"这次难 / 一般 / 顺"：**首版只记录，不影响间隔**。自适应算法留到有真实数据之后再做——现在做等于凭想象调参

### 4.6 存储（一个真实约束）

图片不能进 `localStorage`（配额约 5MB，几张 base64 图就撑爆）。因此：

- **图片**：`IndexedDB`，压缩至 **512px 长边**，**仅保留最近 20 个词**的图；更早的图删除，但**词与事件记录永久保留**
- **事件与词状态**：`localStorage`（体积小）
- 存储写满 → 停止派发新任务并提示导出，**不覆盖历史**

### 4.7 后端与部署

- **一个最小代理服务**：托管静态资源 + 转发视觉/文本模型调用。存在的两个理由——**API 密钥不能进客户端**；局域网自测也需要 HTTPS，代理是解决它的唯一顺路位置
- **手机如何访问**：浏览器只在**安全上下文**下放行 `getUserMedia`——`localhost` 与 HTTPS 域名算，`http://` + 局域网 IP 不算。因此开发期用内网穿透（cloudflared / ngrok）拿真实 HTTPS 域名；自签证书需要每台测试机手动信任且后续仍会被部分浏览器拦，不作为主路径
- 这本来是为 PWA 付出的额外成本，已在选型时说明

## 5. 错误处理与测试（第 3 节）

**贯穿原则：任何失败都不许被静默降级成"好像成功了"。** 一次伪造的反馈就等于污染一个样本。

### 5.1 降级阶梯（每个故障只退到明确的一档）

| 故障 | 界面行为 | 落盘标签 |
|---|---|---|
| 相机未授权 | 说明为何需要相机 + 浏览器设置指引，**不给"随便看看"的假入口** | `blocked_permission` |
| 帧太暗 / 糊 | 当场拦下提示重拍，**不消耗识物调用** | `frame_rejected` |
| 识物超时 / 失败 | 允许重试；**用户第 2 次尝试仍失败**则退到场景词包手选 | `recognize_failed` |
| 反馈接口失败 | 保留原句不丢，进"待反馈"队列，允许稍后补 | `feedback_pending` |
| 模型判 `uncertain` | 如实显示"拿不准" + 改写建议，**不伪装成判定** | `uncertain` |
| 转写不可用 | 降级为"手动打勾：我读过了" | `speech_unsupported` |
| 存储写满 | 停止新任务并提示导出，**不丢历史** | `storage_full` |

**`frame_rejected` 与 `recognize_failed` 是两档**：前者是本系统自己拦的（省调用、省延迟），后者是外部不可控。混在一起统计就分不清该优化什么。

**待反馈队列重试策略（仅适用于 `FeedbackEngine`，与识物重试是两回事）**：失败后自动重试 3 次（间隔 10s / 30s / 90s）；仍失败则保留在队列，界面显示"待补反馈"，用户可手动重试。原句永不丢弃。

**帧质检初值与校准**：亮度均值 `< 40/255` 判太暗；拉普拉斯方差 `< 80` 判模糊。这两个数是**首轮设定值**，不是定论——第一周用真实数据校准，并把每次调整记入变更记录（它们直接影响 `frame_rejected` 与最终 `retry_rate`）。

### 5.2 测试

**自动测只覆盖纯逻辑**（只有它们值得写）：

| 单元 | 用例 |
|---|---|
| `PickWord` | 可接受词集有 3 词时选哪个；多候选同时命中时的取舍 |
| `frameQC` | 合成全黑图、纯噪声图下的判定稳定性 |
| `FeedbackEngine` 响应校验 | 合法 JSON、缺字段、判定值越界、`uncertain` 路径 |
| `DueScheduler` | 到期计算、跨天边界、`maintained` 转换 |
| `EventLog` | 每条事件的 schema 完整性 |

**不写自动测**：相机、转写、真实模型调用——它们是外部依赖，mock 测试只是在测自己写的 mock。

**契约级测试（真正的验收）**：直接复用在册判据。识物链路测 `top3 >= 0.85` 与 `retry_rate <= 0.2`；造句链路用人工标注语料对照 `FeedbackEngine`，测它区分"用词错 / 搭配不当"的准确率。**测完直接 `validation_submit` 回填**——开发动作与验证动作合成一件事，不额外造验收标准。

**明确不写**：集成测试自动化与 CI。搭 CI 的时间会超过它在这 1–2 周内保护的价值。代价是回归只能手动跑一轮闭环。

## 6. 风险与已知弱点

| 风险 | 说明 | 处置 |
|---|---|---|
| 弱网下相机体验 | 快门后若卡住，用户会连按，直接污染 `retry_rate` | 快门后**立即**本地反馈（画面冻结 + 进度），不等网络 |
| iOS 转写不稳 | Web Speech API 支持差异大 | 包在统一接口后，单独打点 `speech_unsupported`；**该不支持率本身就是决策数据**——它决定原生版值不值得做 |
| 识物成本 | 每次识物都是视觉模型调用，成本随人数线性上升 | 端侧帧质检先拦掉废帧；首版人数少，成本可控 |
| 强制感污染数据 | 勉强写完的句子混入样本 | 记录停留时长与改写次数，事后筛出敷衍样本单列 |
| 手选复现占比过高 | 说明"跨场景"主张未被兑现 | 单列 `manual_reacquire` 比例，与 `scene_reacquired` 分开展示 |
| 音准评分缺失 | 契约 `TECHNICAL_CONSTRAINTS` 未满足 | 已在 §4.3 显式标注为妥协，不隐瞒、不以近似冒充 |
