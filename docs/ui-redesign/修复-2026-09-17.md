### 1.4 测试助手的真实缺陷（本轮自己踩到、已修）

新写的断言要量"`textarea` 规则块里有没有 `overflow-wrap`"。第一版助手用**行首锚定**：

```js
new RegExp(`^[^\\n,{}]*${selectorPattern}\\s*\\{([^}]*)\\}`, 'ms')   // ❌ 抓错块
```

它抓到的不是独立规则，而是**合写块**：

```css
input[type='password'],
input[type='text'],
textarea {          /* ← 这一行正好落在一个行首，^ 在此匹配、前缀可为空 */
```

于是助手量的是一个**没有** `overflow-wrap` 的块 ⇒ 断言恒 RED。**根因**：多行选择器列表的
**最后一行**，在文本上与"独占一行的选择器"**无法用行首锚定区分**。

**修法**（`tests/styles.test.mjs` 的 `cssBlock`）：遍历**每一个规则块**，要求它的
**整条选择器列表**与 pattern 精确相等：

```js
const want = new RegExp(`^\\s*${selectorPattern}\\s*$`);
const re = /(?:^|\n)([^{}]*?)\{([^}]*)\}/g;   // 惰性展开 ⇒ m[1] 是完整选择器文本
while ((m = re.exec(cssBody)) !== null) if (want.test(m[1])) return m[2];
```

合写块的 selector 是 `input[…], input[…], textarea`（含逗号、不等于 pattern），天然被排除。
**这不是放宽断言**：§5 的 M4 用它抓到"删掉 `overflow-wrap`"⇒ 仍然 RED（正是为验证这一点做的）。

### 1.5 追加轮：禁用态（总控提缺陷 → 实测否证 → 把真脆点钉住）

总控报告"给 `button.primary` 加 `disabled` 后背景仍是 `rgb(15,118,110)`"，并给出归因：
「`button:disabled` 在 `button.primary` 之前、两者同权重 0,1,1 ⇒ 后面那条 `.primary` 赢；
而 `.primary` 设的是 `--btn-*` 变量、`button:disabled` 设的是属性本身 ⇒ 变量把禁用色整个盖掉」。

**归因不成立，实测见 §4.4**：两者**不争同一个属性**（`background` 只由基础 `button`(0,0,1) 与
`button:disabled`(0,1,1) 两条声明竞争，**权重分胜负、与顺序无关**），所以禁用色没有丢。
总控量到的"没变"是**过渡假象**（见 §4.4 的"立刻读 vs 等 600ms"两列）。

**但仍然做了三件事**（前两件是总控点名的，第三件是我加的）：

1. **规则顺序调整**（总控要求）：`button:disabled` 整块**下移到 `button.primary` 之后**
   （现 `button.primary` 在 `styles.css:333`、`button:disabled` 在 `:352`）。
   为什么**不**按总控原话把 `.primary` 挪到前面：那样会把一条 37 行的 `.primary` 说明注释
   插进基础按钮状态规则中间，可读性代价白付；而"谁在后面"这个性质由下移 `button:disabled`
   同样拿到（效果等价、改动 7 行）。**实测这次顺序调整没有改变任何一个渲染值**——
   重排前后两次全量测量的 JSON **逐字节相同**（`tmp/probes/primary-measure-before-reorder.json`
   vs `primary-measure.json`；`disabled-settled-before-reorder.json` vs `disabled-settled.json`）。
2. **两处注释按实情更正**：`button.primary:disabled` 那条把权重算错了
   （原文写"= 0,2,1，故写作 0,3,1"，实际就是 **0,2,1**），并把"它不是唯一防线、两条互为冗余"
   写清楚；`p.row > button:disabled` 上方那条"压过上面所有变量声明（同权重、写在最后）"
   两句都不成立（本节不是最后；`p.row > button` 现在写在本节之前），已改成实测事实。
3. **新增一条断言 + 四个变异体**（§2 第 10 条、§5 的 M5–M8）。其中**最有价值的是 M6**：
   `button.primary` 若被写成直接声明 `background`（而不是只设 `--btn-*` 变量），
   那条与 `button:disabled` **同权重**且写在后面 ⇒ **靠书写顺序赢** ⇒
   禁用按钮真的会变回满血实心。**我在浏览器里植入 M6 实测确认了这个缺陷成立**：
   禁用后浅色停在 `rgb(15,118,110)`、深色停在 `rgb(79,209,197)`（见 §4.4 末）。
   所以新断言不是理论洁癖——它挡的是一个**能复现的真缺陷**，而且正是总控担心的那个症状。

## 7. 未验证 / 不确定（不许当成"没问题"）

1. **只跑了 Chromium（Edge）**：Firefox / WebKit 本机没装（上一轮已确认 `Executable doesn't exist`）。
   已知受引擎影响的点：`textarea` 的断行默认值（本轮已改成显式声明，**降低**了这项风险）、
   `color-mix()`（焦点环）的支持度。**"其他浏览器上也这样"未验证。**
2. **不是真机**：全部是桌面 Edge 的移动仿真。触屏点击热区、软键盘弹起后的布局、
   真视频流画面比例**都没测**。
3. **状态色对比度大多没算**：`:hover` / `::placeholder` / `:focus-visible` 下的
   前景/背景配对**未核**（静态配色已算，见 §4.3）。
   ⚠️ **`:disabled` 这一项本轮已从不验改成已验**：追加轮在浏览器里量了 8 组
   （6 颗主操作 + 2 颗对照，浅/深各覆盖），渲染值与配对都记在 §4.4。
   **仍未算**的是"禁用态那对颜色的 WCAG 比值"——我只贴了渲染值
   （浅 `rgb(243,240,235)` 底 / `rgb(152,145,138)` 字，深 `rgb(26,25,23)` / `rgb(125,118,110)`），
   没有算比值。**注意这不影响"禁用态不该是重音"这条结论**（那是可比对的渲染值，不是比值）。
   另一处仍缺：**禁用态没有在"应用真的把它禁用"的状态下量过**——
   我是用 `btn.disabled = true` 切换的（`:disabled` 确实匹配上了，实测 `matches(':disabled') === true`），
   而 `ready` 屏真正禁用「拍照」需要 `storageFull()`，走查台没有那一档。CSS 只看伪类是否匹配，
   所以结论成立；但"真跑到存储写满那一档"**没做**。
4. **`pending-empty` 档位没有 ARRIVED 判据**（§4.1 末）：`galleryArrived` 恒为 `null`，
   我只能证明它渲染成 ready 屏，不能证明"这就是它该有的样子"（无设计口径可依）。
5. **`reading` 屏在 `ttsOk === false` 时的分支没测**：那一档只有一颗「跳过跟读」
   （`app.mjs:869`，**不**带 primary），走查台注入的假环境里 `speechSynthesis` 可用，
   所以进的是三按钮分支。那一分支"该不该有主操作"任务书没点名（点的是「我读过了（自评打勾）」），
   我按"不标"处理——**这是判断，不是实测**。
6. **`--ink-faint` 浅色对比度 2.93:1 仍然不达 AA**：本轮任务书明确只清"三个零风险项"，
   这一条**未修**（上一轮已登记，本轮原样保留）。
7. **`:has()` 删除后的老浏览器行为未验**：旧注释声称"不支持 `:has()` 的老浏览器退化为全部次要外观"。
   现在主操作判据是**类名选择器**（所有引擎都有），所以理论上不再依赖 `:has()`；
   但"老浏览器上重音是否出现"我没法实测（没有可用的老引擎）。

## 8. 最后一行结论

**三件事全部做成并在浏览器里实测确认**：`word` 屏要学的词实测为
衬线 `"Iowan Old Style", …, serif` / `32px`（中文标题仍无衬线 `24px`，未被牵连）；
主操作改成显式 `.primary` 类名、两条 `:has()` 猜屏判据已删，**逐档逐颗实测浅色 12 档 30 颗 +
深色 8 档 21 颗按钮**：
六个指定屏各自**恰好一颗** `rgb(15,118,110)`、`pending` 与 `feedback` **零点亮**、**没有任何一屏出现两颗**、
横溢出 0、控制台错误 0（深色下 primary 为 `rgb(79,209,197)`，`--on-accent/--accent` = 9.11:1 达 AA）；
三个零风险清理全部落地（`#16151300` 死代码已删、错按钮名注释已按实测文案更正、`textarea` 已显式声明断行）。
**追加轮（禁用态）的结论是"总控报的缺陷不存在、但那个缺陷是真的"**：
当前代码里禁用后主操作落到沉底灰（浅 `rgb(243,240,235)` / 深 `rgb(26,25,23)`，§4.4 实测），
总控量到的"没变"是 180ms 过渡造成的**测量假象**；而把重音写成直属性（M6）后
**同一个症状确实复现**（禁用后停在 `rgb(15,118,110)`），已被新断言钉住。
**裸 `node --test` = 511 passing / 0 failing**（基线 509/0；口径是裸命令）；
变异校验 **8/8 抓住真实回归**（RED 原文见 §5），恢复后三个文件 sha256 **逐位复原**，
且规则顺序调整经两次全量测量证明**未改变任何渲染值**（重排前后 JSON 逐字节相同）。
**还缺**：Firefox / WebKit 两个引擎、真机（触屏 + 软键盘 + 真视频流）、
`:hover`/`::placeholder`/`:focus-visible` 状态色对比度、禁用态那对颜色的 WCAG 比值、
"应用真的把按钮禁用"（`storageFull()` 那一档）没在走查台上跑到、
`pending-empty` 的到位判据、`reading` 的无 TTS 分支。
